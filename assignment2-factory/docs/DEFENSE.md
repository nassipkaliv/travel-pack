## 3. Part C — Abstract Factory

**Открыть:** `src/main/java/kz/aitu/sdp/trip/factory/TripFactory.java`

> «Abstract Factory создаёт согласованную семью продуктов. Интерфейс объявляет три метода

## 4. Part D — как гарантируется совместимость

Это главный вопрос защиты. Задание запрещает решение «проверить и бросить исключение».

**Открыть:** `family/budget/Hostel.java` — показать первую строку объявления класса.

```java
class Hostel implements Accommodation {   // ← нет public
```

> «Конкретные продукты объявлены package-private и лежат в одном пакете со своей фабрикой.
> Вне пакета `family.budget` выражения `new Hostel()` просто не существует: код не
> скомпилируется. Это гарантия компилятора, а не проверка в рантайме.»

Дальше три уровня защиты:

1. **Продукты не видны снаружи** — нельзя назвать класс по имени.
2. **Единственный источник компонентов — фабрика**, и каждая возвращает продукты своего тарифа.
3. **TripPlanner хранит одну фабрику** и берёт все три компонента из неё:

**Открыть:** `app/TripPlanner.java`, метод `planTrip`

```java
return new TripPlan(factory.tier(),
        factory.createTransport(),
        factory.createAccommodation(),
        factory.createExcursion(),
        request);
```

> «Смешать два семейства физически нечем: другой фабрики у планировщика нет.»

4. **Сравнение тарифов в `TripPlan`** — только страховка на случай плана, собранного
   вручную в обход планировщика.

Итоговая фраза:

> «Комбинация A1 + B2 + C3 не отклоняется проверкой — вне пакета семейства её нельзя
> даже написать. Это доказано тестом `concreteProductsAreNotVisibleOutsideTheirFamilyPackage`,
> который через рефлексию убеждается, что классы продуктов не public.»

## 5. Part B — Factory Method

**Открыть:** `booking/BookingChannel.java`

> «Вторая ось — канал продажи. Здесь Factory Method. Creator — это `BookingChannel`,
> у него три наследника: онлайн, агентство и корпоративный канал. Product — это
> `BookingDocument`: e-mail ваучер, бумажный ваучер и счёт на компанию.»

```
BookingDocument (Product)      BookingChannel (Creator)
├── EmailVoucher               ├── OnlineBookingChannel
├── PaperVoucher               ├── AgencyBookingChannel
└── CorporateInvoice           └── CorporateBookingChannel
```

> «Задание требует, чтобы Creator содержал осмысленную бизнес-логику, а не просто
> `return new Product()`. Метод `book()` общий для всех каналов и делает четыре вещи,
> и только одна из них — вызов фабричного метода.»

```java
public final Booking book(TripPlan plan, Quote quote, Customer customer) {
    requireGroupFits(plan, customer);          // группа больше, чем вмещает экскурсия?
    int price = finalPrice(quote, customer);   // правила цены канала
    String reference = nextReference();        // номер брони из счётчика канала
    BookingDocument document =
        createDocument(plan, customer, price, reference);   // ← фабричный метод
    return new Booking(reference, plan, customer, price, paymentDeadlineDays(), document);
}
```

> «А метод `confirmationMessage()` использует созданный документ: берёт его формат и флаг
> подписи. То есть Creator не обёртка над `new`, он работает с продуктом.»

| Канал | Цена | Документ | Оплата |
|---|---|---|---|
| Online | −3 % | e-mail ваучер | сразу |
| Agency | +5 % сбор | бумажный ваучер с подписью | 3 дня |
| Corporate | −7 % от 5 человек | PDF-счёт на компанию | 30 дней |

### Если спросят: почему Factory Method, а не статическая фабрика?

> «Четыре причины.
> **Первая:** `book()` написан один раз и работает для каналов, которых ещё не
> существовало. Статической фабрике понадобился бы switch по названию канала прямо
> внутри этой логики.
> **Вторая:** у канала есть состояние — счётчик номеров броней, ONL-0001, ONL-0002.
> У статического метода состояния нет.
> **Третья:** подкласс переопределяет не только создание документа, но и цену, и срок
> оплаты. Поведение канала — единое полиморфное целое.
> **Четвёртая:** в тестах можно подставить свой наследник `BookingChannel`. Статический
> метод подменить нельзя.»

## 12. Короткие ответы на возможные вопросы

| Вопрос | Ответ |
|---|---|
| Чем Factory Method отличается от Abstract Factory? | Factory Method — один метод, который подкласс переопределяет, чтобы создать один продукт. Abstract Factory — объект, создающий целую семью связанных продуктов. |
| Почему клиент не создаёт продукты сам? | Он не знает их классов и не должен: иначе возвращаются все четыре проблемы из Part A. |
| Где здесь принцип открытости/закрытости? | Новая семья — это новый пакет; существующий код не меняется, кроме одной строки реестра. |
| Что произойдёт, если фабрика вернёт чужой продукт? | Такой код не скомпилируется вне пакета семьи, а если собрать план вручную — сработает проверка тарифа в `TripPlan`. |
| Почему интерфейсы продуктов, а не абстрактные классы? | У продуктов нет общего состояния или готового поведения, только контракт. Общая часть вынесена в `TripComponent`. |
| Зачем `TripComponent.tier()`? | Чтобы план мог проверить согласованность и чтобы бизнес-логика могла писать тариф в документы. |
| Что в проекте от первого задания? | Домен туров. Там был Builder для одного сложного объекта, здесь — создание семейств продуктов. |
